# Live tests L1 and L2, 2026-11-16

The owner approved both packages on 2026-11-16 (see
`docs/plans/2026-11-15-implementation-plan.md`, C1 and C2). Each ran
within its cap. Raw outputs stayed private, outside the repository. The
files here are whitelisted copies written by `normalize.py`, which keeps
named fields only and drops session, account, host, installation and
path fields, hook output, message text and the time zone. The
coordinator inspected them before committing.

## L1: Claude usage reading

Client: Claude Code 2.1.325, model `claude-opus-5-5`, subscription
login. Calls: two `claude -p` invocations, no retries, each in a fresh
empty directory.

1. Statusline capture. One temporary line in the owner's statusline
   script appended the capture time and `rate_limits` to a private file
   during this session. The original script was backed up first and
   restored afterward, and its SHA-256 matches the original
   (`e292f453...`). The input has `rate_limits.five_hour` and
   `rate_limits.seven_day`, each with `used_percentage` (whole points)
   and `resets_at` (Unix seconds). Copy: `l1-2026-11-16/statusline.jsonl`.
2. `claude -p "Reply with the single word: ok" --output-format
   stream-json --verbose --max-turns 1`: exit 0, one turn. The stream
   includes a `rate_limit_event` on this ordinary run. Its
   `rate_limit_info.unifiedWindows` gives `five_hour` and `seven_day`,
   each with `utilization` (a fraction: 0.05 means 5 percent),
   `resetsAt` and `status`, alongside top-level `status`, `resetsAt`,
   `rateLimitType` and overage fields. The `result` reports 2 input
   tokens, 4 output tokens, 11,370 cache-read and 16,548 cache-creation
   tokens, and `total_cost_usd` 0.134746 (list price; the subscription
   is not billed per call). Copy: `l1-2026-11-16/l1-stream.jsonl`.
3. `claude -p "/usage" --output-format json`: exit 0, `num_turns` 0,
   zero tokens, `total_cost_usd` 0. It reports three windows: the
   current session (five-hour), the current week for all models, and
   the current week for Fable, each with a percentage and a reset time
   in local time. Copy: `l1-2026-11-16/l1-usage.jsonl` (window lines
   only).

Measured consumption. The five-hour reading in the statusline went from
5 to 6 between the captures that bracket command 2 (capture times
1794865607 and 1794865616; the command ran from 1794865607 to
1794865611). That interval also includes this interactive session's own
turns on the same account, so command 2 used at most one point; whole
points cannot resolve less. Across command 3 the reading stayed at 6,
and the client reported no turn and no tokens. The weekly reading stayed
at 23 in the statusline while `/usage` reported 24 at about the same
time, so the two sources round or refresh differently.

Results against the package:

- Foreman's own stream yields a usable reading: `rate_limit_event`
  includes a used fraction and a reset time per window on an ordinary
  run. Once O11 is decided, sequential launches can chain on readings
  from foreman's own steps.
- `/usage` made no model turn here and reported zero tokens. It is a
  candidate read without a turn. One observation at whole-point
  resolution does not show that it never consumes usage, so the plan
  keeps treating it as possibly consuming until repeated reads show
  otherwise.
- The readings have whole-point resolution. A step that uses less than
  one point leaves no measurable trace in a single before-and-after pair.
- `/usage` reports a third window (weekly, Fable). The statusline and
  the stream event do not include it.
- `--max-budget-usd` exists in `claude --help`. Its unit is dollars;
  subscription points have no flag.

## L2: Codex usage windows

Client: codex-cli 0.167.0, ChatGPT login (existing authentication; no
credential was read or extracted).

Protocol check, offline. `codex app-server generate-json-schema`
produced the installed client's protocol. It defines `initialize`
(requires `clientInfo` with `name` and `version`), the `initialized`
notification and `account/rateLimits/read`. The response gives
`rateLimits` and `rateLimitsByLimitId`, each with `primary` and
`secondary` windows of `usedPercent` (integer), `windowDurationMins` and
`resetsAt`. The same protocol also defines
`account/rateLimitResetCredit/consume`, which spends a reset credit;
`read_limits.py` allows only the three methods above and was never able
to send it.

Free read first. The newest local Codex session file already showed the
window shapes: primary 300 minutes, secondary 10,080 minutes.

Calls: two app-server reads and one `codex exec`, no retries.

1. Read before: primary 0 percent (300 minutes), secondary 13 percent
   (10,080 minutes), `ordinaryUsageAllowed` true. The server sent one
   notification, `remoteControl/status/changed`; no turn started.
2. `codex exec --json --sandbox read-only --skip-git-repo-check "Reply
   with the single word: ok"`: exit 0. Events: `thread.started`,
   `turn.started`, one `agent_message` item, `turn.completed` with
   usage of 22,308 input tokens (13,440 cached) and 5 output tokens.
3. Read after: primary 1 percent, secondary 13 percent. Notifications:
   `remoteControl/status/changed` and `account/updated`; no turn
   started.

Measured consumption: one short `codex exec` moved the primary window
from 0 to 1 percent and left the secondary at 13. Codex was otherwise
idle, so the point is attributable to the run, at whole-point
resolution.

Results against the package:

- The app-server read returns used percent, window length and reset time
  for both Codex windows and starts no turn. A waiting Codex step can
  read on an interval (O3).
- `turn.completed` reports token usage, which gives the rate fit (B17)
  its Codex inputs.
- Reset times moved while idle. The session file showed the primary
  window resetting at 1794883472; the first read, at 0 percent, showed
  1794883493; after the run it stayed at 1794883493. This suggests that
  an unused Codex window's reset time rolls forward until usage starts.
  Two observations support it, so it is an inference. It matters to the
  design: revision 6.1 opens a period on a reading with a later reset
  time, and a rolling reset time would open periods while the window is
  idle. This needs an owner decision before the Codex windows enter the
  default policy.
- `ordinaryUsageAllowed` is a provider flag that its schema says clients
  must not infer from percentages or reset times.
