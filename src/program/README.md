# Program

See [how it works](../../docs/how-it-works.md).

May import: `domain`, `features`, `format`, `runtime`.

Per the [design](../../docs/plans/2026-11-14-agent-supervisor-design.md) ("Architecture"), this layer wires the Runtime capabilities into use cases with Features and Format. It is the only layer that sees all of them, which is why the layer table lets it import all four. It decides nothing itself.

## Admission and settling

[`admission.ts`](admission.ts) runs each ledger decision in one transaction and leaves the deciding to Features. `admit` reads every row and passes them to `decideAdmission` ([`features/admission.ts`](../features/admission.ts)). It writes any spend-down expiries the decision returns, then the request's `Grant` if admitted. `cancelLostRace` cancels a grant whose `Intended` lost the log's compare-and-append. `applySettle` writes what `settleActions` decides; `settleRowOf` turns a charge for a finished step or an owner-ended one into a `Charged` at the estimate, and an orphan into a cancel. If a transaction fails, it writes nothing. Admission bounds foreman's own launches and reservations; it does not keep the provider's count below the cap.

## Worktree startup check

[`worktree.ts`](worktree.ts) wires the supervisor worktree. `createWorktree` sequences creation. It first requires an absolute path. It reads the owner's HEAD and common directory, then runs the attribute check of [`attribute-sources.ts`](attribute-sources.ts) on the base and the owner's repository, which fails with `AttributeSourcesRefused` before `git worktree add` (plan B11c). It reads the branch probe and the path's `stat` through Runtime, decodes with Format, and gives the results to the Features prechecks. Then it runs the add, decodes the reads taken after it, and runs `checkCreated`. It lives here because Runtime may not import Features. `identifyWorktree` lists the worktrees from the recorded common directory, reads the recorded directory, decodes both and passes them to `checkWorktree`; when that passes, it runs the attribute check inside the supervisor worktree against the recorded base, so a `core.attributesFile` in that worktree's `config.worktree` is seen. Neither cleans up, prunes or unlocks anything. `worktreeProgramWith(start, allowance)(home)` builds both over the clean and pinned runners of [`runtime/git.ts`](../runtime/git.ts), with the empty home directory the caller owns, and both attribute checks judge the root `.gitattributes` under `allowance` (owner decision M09, option a). The exported `worktreeProgram` is `worktreeProgramWith(startGit, noAttributeAllowance)`, which permits no line, and `test/program/git-coverage.test.ts` checks that definition on the syntax tree and drives the same factory with a recording process call. The CLI's production wiring does not use `worktreeProgram`: [`production.ts`](production.ts) builds `worktreeProgramWith(startGit, config.attributeAllowance)`, with the allowance from the configuration file. `createWorktreeWith(run, allowance)` and `identifyWorktreeWith(run, pinTo, allowance)` take any runners, for tests.

### Which git commands are pinned

The startup attribute check runs through the pinned runner (plan B11d), built from the recorded `WorktreeCreated` after `checkWorktree` passes, with the supervisor worktree as its directory. Its four commands get `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR` from the record: `git ls-tree --full-tree -r -t -z <base>`, `git cat-file blob <object>` for each `.gitattributes` blob, `git config --get core.attributesFile` and `git config --get-regexp '^includeif\.'`. Every other command stays on the clean runner. That covers all of creation: the owner's `rev-parse` reads, its attribute check, the branch probe, `worktree add` and the reads after it. It also covers the startup check's `worktree list` and its two identity `rev-parse` reads; `stat` is not a git command. Those identity reads must discover the repository on their own: pinned to the recorded values they would print those values back and could not see a moved `.git` file or another repository at the path. Two later uses run in the supervisor worktree too. The session commands' worktree check, in [`production.ts`](production.ts), runs `identifyWorktree` and then reads the worktree's HEAD with `git rev-parse HEAD` through the pinned runner. The snapshot runs every command through the snapshot runner, which is the pinned runner plus `GIT_INDEX_FILE`.

## Snapshot

[`snapshot.ts`](snapshot.ts) wires the snapshot (plan A2). `snapshotProgramWith(start)(home)(identity)` runs in the supervisor worktree, with git pinned to the recorded identity and a fresh temporary index in the state directory. It refuses a repository whose object format is not SHA-1. Then [`snapshot-preflight.ts`](snapshot-preflight.ts) runs before anything is staged (review finding B08, M14). It lists the base revision's tree and the paths git ignores, then walks the worktree from its top level with `readdir` and `lstat`, never through a link at a walked entry. `walkSteps` in Features decides what each directory means. Coverage is what `add -A` over the base covers: every base path and the directories above it, plus what git does not ignore. Where Features says to ask, `git check-ignore` decides whether a directory or a finding is ignored. A gitlink in the base tree, a covered directory holding `.git` and a covered FIFO, socket or device each refuse the snapshot with `SnapshotPreflightRefused`, which lists every finding, and `read-tree`, `add` and `write-tree` never run. Without the preflight, `add -A` would drop a special file without a word and would stage a nested repository as a gitlink or fail on it. [`snapshot-steps.ts`](snapshot-steps.ts) holds the git steps both parts share. Only after the preflight does the snapshot run `read-tree <base>`, `add -A`, `write-tree` and `ls-tree -r -z <tree>`. It reads every entry on disk without following a link at its own path (Runtime), computes blob ids (Format) and passes both to `judgeSnapshot` (Features). It succeeds with the tree id when every entry passes, and fails with `SnapshotRefused`, with the tree and every mismatch, when one does not. The snapshot covers the tracked and untracked files git does not ignore. It leaves out ignored files, empty directories, the git directory and anything outside the worktree. Staging writes blob and tree objects, but the worktree's own index is never read or written and no ref moves. The walk and the reads assume the assisted rung's quiescence, with no concurrent writer in the worktree (review limit L02). `snapshotProgram` is the same over `startGit`.

## Assisted session commands

These modules run the commands of slices A1 and A2. Each command but `status` takes the lock, reads the whole log, folds the session and asks `allowed` in Features before it writes, and a launch or a close runs the settle step first; [`command-start.ts`](command-start.ts) holds those reads. Every log write is one atomic batch at the position the command last read or wrote, and a file is published before the record that names it. A failure stops the command and writes nothing more; nothing is replayed. [`session-errors.ts`](session-errors.ts) holds the typed failures, each stating what was written before it.

[`attempt.ts`](attempt.ts) holds `runAttempt`, the launch protocol a `LaunchPlan` drives:

1. The rules, checked before anything is staged. The plan's facts say whether the owner gave `--attest` and whether the session's reports are intact, and they presume the snapshot passes: for `review` any passing snapshot, for `correct` one on the reviewed tree. A command refused here runs no git command and writes no git object.
2. The plan's snapshot step, only after the rules allow the command. For `review` and `correct` it runs the attribute-source check again through the pinned runner, then takes the snapshot, and the rules are checked again with the snapshot taken. A snapshot that fails the raw checks, or a tree that is not the reviewed one, refuses the command with nothing appended. `implement` takes no snapshot.
3. Admission and the waiver step ([`attempt-admission.ts`](attempt-admission.ts)). A waiver armed for the provider is used first. Otherwise admission decides, and a pacing refusal appends batch Q, the quota hold. Under a quota hold, a launch without `--waive` stops with `QuotaHeld` and the owner's consent is not consumed. With `--waive`, batch W arms the waiver and admission runs with it, unless a waiver is already armed for another provider (`WaiverRefused`).
4. Batch I: the plan's consent events, then `Intended`. If the log moved, the grant is canceled as a lost race (`LostRace`) and nothing launches.
5. [`attempt-run.ts`](attempt-run.ts) starts the client with its fixed profile in the supervisor worktree, with the parent's environment minus every `GIT_*` variable, and appends batch L, the `Launched`. The raw output streams into `<raw>.streaming`. Once the leader exits, the raw file and the handoff file are published, then whatever the plan derives from the handoff (a review's findings draft). Features classifies the outcome from the lines [`client-output.ts`](client-output.ts) decoded; every malformed line is carried to classification and makes the attempt `Unclassified`, while event types that bear no outcome are passed over. Batch F then appends `Finished` with its `ReportRecorded`.
6. The settle step runs again, so the grant is charged at its estimate.

There are three plans. [`implement.ts`](implement.ts) has no handoff facts, no snapshot and no consent events. Its brief is Format's implementer brief of the session's recorded task file, checked against its hash (`TaskFileChanged`). It launches Claude's editing profile, and its handoff is Claude's final result text.

[`review.ts`](review.ts) runs `review [--waive] --attest` after a usable implement or correct. Batch I is `SnapshotTaken`, `HandoffApproved` and `Intended`. The brief holds the recorded task, the tree, the base revision, the changed paths from `git diff-tree -r -z --name-status` through the pinned runner (`ChangedPathsUnread` when that fails), the previous attempt's recorded handoff and the coverage statement. Codex runs with its read-only profile, and its final message, read from the file Codex was told to write, is the handoff. Only a missing file means Codex gave no message and the handoff is empty; a file that is there but cannot be read stops the command before batch F. When the message's findings block decodes, the review publishes it as the session's draft, `<sessionId>.findings-draft.md`, for the owner to edit.

[`correct.ts`](correct.ts) runs `correct --findings <file> [--waive] --attest` after a review that asked for changes. Batch I is `ReviewChecked`, `HandoffApproved` and `Intended`. Only the owner's findings file reaches the corrector: it is copied into the state directory as `<sessionId>.<reviewOpId>.findings.md` and its SHA-256 goes into `HandoffApproved` (`FindingsFileUnreadable` when it cannot be read). The brief's prior handoff is the last implementer's or corrector's. The reviewer's final message holds the reviewer's own findings, so it is left out.

[`handoff-facts.ts`](handoff-facts.ts) holds what the handoff commands read: the facts and the presumed snapshots, whether every finished attempt has its report recorded for this session with both files intact, and `takeSnapshot`, which turns a raw-check refusal into a snapshot that did not pass. [`handoff-git.ts`](handoff-git.ts) builds the handoff's git work for a recorded worktree: the attribute check, the snapshot and the changed paths, each pinned to the session's recorded identity. [`recorded-files.ts`](recorded-files.ts) reads a file the log records and checks its hash first (`RecordedFileChanged`).

[`handoff.ts`](handoff.ts) holds the handoff commands that launch nothing. `reject [--note]` appends `HandoffRejected` for a usable attempt awaiting its handoff, after which only `close --abandoned` remains. `closeFinished`, behind `session close --finished --attest`, runs the settle step and checks its rules with the snapshot presumed on the reviewed tree. Only then does it run the attribute check and take the snapshot. When the tree is still the reviewed one, it appends `ReviewChecked`, `SessionClosed` with the attestation and a `WaiverExpired` for every armed waiver, in one batch.

[`session.ts`](session.ts) holds the other commands that launch nothing. `openSession` publishes a copy of the task file and appends `SessionOpened` and `Approved` for the tranche at the worktree's HEAD. `stepEnded` appends `StepEndedByOwner` at the wall clock's time. `closeSession` closes `--abandoned` or `--interrupted`: it runs the settle step, then appends `SessionClosed` and a `WaiverExpired` for every armed waiver. It releases no hold, deletes no file and changes grants only through settlement. Of these, only `session open` needs the worktree check, so `step-ended` and `close` stay available when the worktree or a client is broken.

[`status.ts`](status.ts) builds the status report without the lock and without writing to the log or the ledger. It shows the session state, each incomplete attempt with its grant and advisory process evidence, the holds in place, the armed waivers, each client's pin check, the worktree check and the integrity of each recorded report file. Every report that shows evidence states that it is advisory.

[`worktree-command.ts`](worktree-command.ts) holds `createRecordedWorktree`, behind `foreman worktree create`. Plan "Slice A1" does not name this command; it exists because a session needs a recorded worktree. Under the lock it refuses when the log already records a worktree (`WorktreeAlreadyRecorded`), so creation runs at most once. Otherwise it creates the worktree and appends `WorktreeCreated`. It does not write `WorktreeIntended` or recover anything. A crash between the add and the append leaves a worktree the log does not record; the next creation refuses its branch or path, and the owner resolves that.

[`session-context.ts`](session-context.ts) declares what a command runs over: the injected capabilities, such as the log, the ledger, the lock, `StartClient` and the worktree check, and the settings from the configuration. [`production.ts`](production.ts) builds them: it decodes the configuration file, opens the log, the ledger and the lock in the state directory, and wires every capability from Runtime. The state directory also holds the session's published files and `git-home`, the empty `HOME` every git command runs with. Each handoff's git work runs through `handoffGitWith(startGit, config.attributeAllowance)`. The monotonic clock is not wired yet (`nowMono` is none), so pacing answers Unknown and every launch needs `--waive`.
