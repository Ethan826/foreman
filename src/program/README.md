# Program

See [how it works](../../docs/how-it-works.md).

May import: `domain`, `features`, `format`, `runtime`.

Per the [design](../../docs/plans/2026-11-14-agent-supervisor-design.md) ("Architecture"), this layer wires the Runtime capabilities into use cases with Features and Format. It is the only layer that sees all of them, which is why the layer table lets it import all four. It decides nothing itself.

## Admission and settling

[`admission.ts`](admission.ts) runs each ledger decision in one transaction and leaves the deciding to Features. `admit` reads every row and passes them to `decideAdmission` ([`features/admission.ts`](../features/admission.ts)). It writes any spend-down expiries the decision returns, then the request's `Grant` if admitted. `cancelLostRace` cancels a grant whose `Intended` lost the log's compare-and-append. `applySettle` writes what `settleActions` decides; `settleRowOf` turns a charge for a finished step or an owner-ended one into a `Charged` at the estimate, and an orphan into a cancel. If a transaction fails, it writes nothing. Admission bounds tarlatan's own launches and reservations; it does not keep the provider's count below the cap.

## Worktree startup check

[`worktree.ts`](worktree.ts) wires the supervisor worktree. `createWorktree` sequences creation. It first requires an absolute path. It reads the owner's HEAD and common directory, then runs the attribute check of [`attribute-sources.ts`](attribute-sources.ts) on the base and the owner's repository, which fails with `AttributeSourcesRefused`, or with `AttributeSourcesUnread` when a source could not be read and nothing read was refused, before `git worktree add` (plan B11c). It reads the branch probe and the path's `stat` through Runtime, decodes with Format, and gives the results to the Features prechecks. Then it runs the add, decodes the reads taken after it, and runs `checkCreated`. It lives here because Runtime may not import Features. `identifyWorktree` lists the worktrees from the recorded common directory, reads the recorded directory, decodes both and passes them to `checkWorktree`. An identity read that git could not complete, such as one that exits on an I/O error, fails with `GitCommandFailed` and git's diagnostic and is never judged; only git's report that there is no repository at the path reaches `checkWorktree` (focused re-review finding 1); when that passes, it runs the attribute check inside the supervisor worktree against the recorded base, so a `core.attributesFile` in that worktree's `config.worktree` is seen. Neither cleans up, prunes or unlocks anything. `worktreeProgramWith(start, allowance)(home)` builds both over the clean and pinned runners of [`runtime/git.ts`](../runtime/git.ts), with the empty home directory the caller owns, and both attribute checks judge the root `.gitattributes` under `allowance` (owner decision M09, option a). The exported `worktreeProgram` is `worktreeProgramWith(startGit, noAttributeAllowance)`, which permits no line, and `test/program/git-coverage.test.ts` checks that definition on the syntax tree and drives the same factory with a recording process call. The CLI's production wiring does not use `worktreeProgram`: [`production.ts`](production.ts) builds `worktreeProgramWith(startGit, target.attributeAllowance)`, with the allowance of the bound target. `createWorktreeWith(run, allowance)` and `identifyWorktreeWith(run, pinTo, allowance)` take any runners, for tests.

### Which git commands are pinned

The startup attribute check runs through the pinned runner (plan B11d), built from the recorded `WorktreeCreated` after `checkWorktree` passes, with the supervisor worktree as its directory. Its four commands get `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR` from the record: `git ls-tree --full-tree -r -t -z <base>`, `git cat-file blob <object>` for each `.gitattributes` blob, `git config --get core.attributesFile` and `git config --get-regexp '^includeif\.'`. Every other command stays on the clean runner. That covers all of creation: the owner's `rev-parse` reads, its attribute check, the branch probe, `worktree add` and the reads after it. It also covers the startup check's `worktree list` and its two identity `rev-parse` reads; `stat` is not a git command. Those identity reads must discover the repository on their own: pinned to the recorded values they would print those values back and could not see a moved `.git` file or another repository at the path. Two later uses run in the supervisor worktree too. The session commands' worktree check, in [`production.ts`](production.ts), runs `identifyWorktree` and then reads the worktree's HEAD with `git rev-parse HEAD` through the pinned runner. It then runs the attribute check, pinned too, on the open session's base, or on that HEAD when no session is open (batch review B07), so a commit made in the worktree after its creation is judged before a session opens on it. The check returns the HEAD and never compares it with the base. While a session is open, the command rules refuse a HEAD that differs from the session's base with `HeadMoved` (owner ruling of 2026-11-23). This replaced B07's earlier behavior, in which a launch ignored a moved HEAD; the attribute check still judges the base. The snapshot runs every command through the snapshot runner, which is the pinned runner plus `GIT_INDEX_FILE`.

## Snapshot

[`snapshot.ts`](snapshot.ts) wires the snapshot (plan A2). `snapshotProgramWith(start)(home)(identity)` runs in the supervisor worktree, with git pinned to the recorded identity and a fresh temporary index in the state directory. It refuses a repository whose object format is not SHA-1. Then [`snapshot-preflight.ts`](snapshot-preflight.ts) runs before anything is staged (review finding B08, M14). It lists the base revision's tree and the paths git ignores, then walks the worktree from its top level with `readdir` and `lstat`, never through a link at a walked entry. `walkSteps` in Features decides what each directory means. Coverage is what `add -A` over the base covers: every base path and the directories above it, plus what git does not ignore. Where Features says to ask, `git check-ignore` decides whether a directory or a finding is ignored. A gitlink in the base tree, a covered directory holding `.git` and a covered FIFO, socket or device each refuse the snapshot with `SnapshotPreflightRefused`, which lists every finding, and `read-tree`, `add` and `write-tree` never run. Without the preflight, `add -A` would drop a special file without a word and would stage a nested repository as a gitlink or fail on it. [`snapshot-steps.ts`](snapshot-steps.ts) holds the git steps both parts share. Only after the preflight does the snapshot run `read-tree <base>`, `add -A`, `write-tree` and `ls-tree -r -z <tree>`. It reads every entry on disk without following a link at its own path (Runtime), computes blob ids (Format) and passes both to `judgeSnapshot` (Features). It succeeds with the tree id when every entry passes, and fails with `SnapshotRefused`, with the tree and every mismatch, when one does not. The snapshot covers the tracked and untracked files git does not ignore. It leaves out ignored files, empty directories, the git directory and anything outside the worktree. Staging writes blob and tree objects, but the worktree's own index is never read or written and no ref moves. The walk and the reads assume the assisted rung's quiescence, with no concurrent writer in the worktree (review limit L02). `snapshotProgram` is the same over `startGit`.

## Assisted session commands

These modules run the commands of slices A1 and A2. Each command but `status` takes the lock, reads the whole log, folds the session and asks `allowed` in Features before it writes, and a launch or a close runs the settle step first; [`command-start.ts`](command-start.ts) holds those reads. Every log write is one atomic batch at the position the command last read or wrote, and a file is published before the record that names it. A failure stops the command and writes nothing more; nothing is replayed. [`session-errors.ts`](session-errors.ts) holds the typed failures, each stating what was written before it.

[`attempt.ts`](attempt.ts) holds `runAttempt`, the launch protocol a `LaunchPlan` drives:

1. The rules, checked before anything is staged. The plan's facts say whether the owner gave `--attest` and whether the session's reports are intact, and they presume the snapshot passes: for `review` any passing snapshot, for `correct` one on the reviewed tree. A command refused here runs no git command and writes no git object.
2. The plan's snapshot step, only after the rules allow the command. For `review` and `correct` it runs the attribute-source check again through the pinned runner, then takes the snapshot, and the rules are checked again with the snapshot taken. A snapshot that fails the raw checks, or a tree that is not the reviewed one, refuses the command with nothing appended. `implement` takes no snapshot.
3. Admission and the waiver step ([`attempt-admission.ts`](attempt-admission.ts)). A waiver armed for the provider is used first. Otherwise admission decides, and a pacing refusal appends batch Q, the quota hold. Under a quota hold, a launch without `--waive` stops with `QuotaHeld` and the owner's consent is not consumed. With `--waive`, batch W arms the waiver and admission runs with it, unless a waiver is already armed for another provider (`WaiverRefused`). An attempt stopped by a deliberate refusal launched nothing, so after the refusal it appends a `WaiverExpired` for every armed waiver ([`waiver-expiry.ts`](waiver-expiry.ts), the one-attempt rule; review findings B15 and R01). `isRefusal` says which failures are refusals. The rules' own refusals count, among them a worktree the startup check judged unready. So do a missing or changed recorded file, a missing findings file, a file that is not UTF-8, an unsafe profile path, a check command the profile refuses (`CheckCommandRefused`, owner ruling of 2026-11-24), refused attribute sources and the snapshot's refusals. Attribute sources are refused when any source that was read is refused, even beside one that could not be read. When a failed read is the only reason to stop, the check fails with `AttributeSourcesUnread`, which keeps the read's diagnostic. Every armed waiver then stays armed, at startup as in the candidate check (the owner's B11c and R01 ruling of 2026-11-20). A failed store, file read, git command or process leaves the waivers armed, as a crash does, so the retry after batch W still uses its waiver. Such a failure keeps its own tag all the way to `isRefusal` (focused review of R01). The startup check fails with `GitCommandFailed`, `GitOutputUndecodable`, `PathUnreadable` or `AttributeSourcesUnread` when it could not run, and with `WorktreeUnready` only when it judged the worktree. A recorded file or findings file that cannot be read fails with `StateFileFailed`; only a missing file is `TaskFileChanged`, `RecordedFileChanged` or `FindingsFileUnreadable`. `runAttempt` accepts only plans whose failures are in `AttemptStop`, the union `isRefusal` covers, so a new failure does not compile until it is classified. The next `--waive` is then accepted.
4. The brief's exact bytes are published as `<sessionId>.<opId>.brief.md`; a failed publication stops the command before batch I, and the next settle step cancels the grant as an orphan. Batch I: the plan's consent events, `Intended`, the `BriefRecorded` with the brief file's path and SHA-256, then a `WaiverExpired` for every armed waiver the `Intended` does not name, such as another provider's. If the log moved, the grant is canceled as a lost race (`LostRace`) and nothing launches.
5. [`attempt-run.ts`](attempt-run.ts) starts the client, with the brief text decoded from the published bytes, so that the argv holds exactly the recorded bytes, with its fixed profile in the supervisor worktree, with the parent's environment minus every `GIT_*` variable, and appends batch L, the `Launched`. The raw output streams into `<raw>.streaming`. Once the leader exits, the raw file and the handoff file are published, then whatever the plan derives from the handoff (a review's findings draft). Features classifies the outcome from the lines [`client-output.ts`](client-output.ts) decoded; every malformed line is carried to classification and makes the attempt `Unclassified`, while event types that bear no outcome are passed over. A stdout line that is not UTF-8 is malformed, and the owner sees a notice in its place; the raw file keeps its bytes (review finding R04). The handoff's text is strict UTF-8 too. A handoff that is not UTF-8 is still published byte for byte. The plan derives nothing from it, and a review's findings count as malformed, so the review is `Unclassified`. Text read from the brief, the recorded task, a recorded handoff or the owner's findings file is strict as well. Bytes that are not UTF-8 refuse the command with `FileNotUtf8` (`FindingsFileUnreadable` for the findings file). Batch F then appends `Finished` with its `ReportRecorded`.
6. The settle step runs again, so the grant is charged at its estimate.

A launch waits until the client's output closes, which can be later than the leader's exit. A process the client started that inherits its stdout or stderr keeps the output open, so the command does not return while that process lives, and it holds the project lock meanwhile. Tarlatan never signals a client or its descendants. The owner's rule for this case (owner ruling on L01, 2026-11-20) is to interrupt tarlatan. The attempt is then left incomplete: `Intended` and `Launched` are recorded and `Finished` is not. `status` shows the attempt with its process evidence. Once the owner has established that its processes stopped, `step-ended <opId> --grant <grantId>` records that, and `session close --interrupted` closes the session. `test/program/inherited-pipe.test.ts` runs a real leader whose descendant holds the pipe, for both halves of the rule.

There are three plans. [`implement.ts`](implement.ts) has no handoff facts, no snapshot and no consent events. Its brief is Format's implementer brief of the session's recorded task file, checked against its hash (`TaskFileChanged`). It launches Claude's editing profile, and its handoff is Claude's final result text.

Claude's editing profile is published by [`claude-profile.ts`](claude-profile.ts) (batch review B03, owner ruling of 2026-11-20). `implement` and `correct` call the `publishClaudeProfile` capability in their prepare step. The call comes after the rules allow the command and before admission. It passes the session's recorded git identity, `session.opened.worktree`. That identity names the worktree's path, its own git directory and the common git directory. It also passes `settings.checkCommands`, the check commands from the configuration (dogfood-3b). The command gives the same list to the brief, so the brief names exactly the commands the profile allows. In production the capability renders Format's fixed template for that identity and those commands. A check command the template refuses stops the launch with `CheckCommandRefused`, a refusal. The decoder refuses such a command first, so it reaches the template only if decoding was bypassed. The template's sandbox denies writes to both git directories (owner ruling of 2026-11-23). The capability publishes the result atomically at `<stateDir>/claude-settings.json`. It replaces whatever was there. Claude's argv then names that file with `--settings`, so the client reads the bytes just published. The argv also passes `--setting-sources project,local` and `--strict-mcp-config` (owner ruling of 2026-11-20, L03). With the first, the owner's user settings and hooks stay out. With the second, no MCP server starts, claude.ai connectors included. L3 path A ran with these flags on 2026-11-22 (`research/live/l3-subset/results.md`); its C4 result motivated the git-directory denials. The rerun of 2026-11-24 showed that they hold: `git commit`, `git update-ref`, `git hash-object -w` and writes to the index and HEAD all fail inside the Bash sandbox (same file, second section). The configuration cannot supply a settings file. A command the rules refuse publishes nothing.

[`review.ts`](review.ts) runs `review [--waive] --attest` after a usable implement or correct. Batch I is `SnapshotTaken`, `HandoffApproved` and `Intended`. The brief holds the recorded task, the tree, the base revision, the changed paths from `git diff-tree -r -z --name-status` through the pinned runner (`ChangedPathsUnread` when that fails), the previous attempt's recorded handoff and the coverage statement. Codex runs with its read-only profile, and its final message, read from the file Codex was told to write, is the handoff. Only a missing file means Codex gave no message and the handoff is empty; a file that is there but cannot be read stops the command before batch F. When the message's findings block decodes, the review publishes it as the session's draft, `<sessionId>.findings-draft.md`, for the owner to edit.

[`correct.ts`](correct.ts) runs `correct --findings <file> [--waive] --attest` after a review that asked for changes. Batch I is `ReviewChecked`, `HandoffApproved` and `Intended`. Only the owner's findings file reaches the corrector: it is copied into the state directory as `<sessionId>.<reviewOpId>.findings.md` and its SHA-256 goes into `HandoffApproved` (`FindingsFileUnreadable` when it cannot be read). The brief's prior handoff is the last implementer's or corrector's. The reviewer's final message holds the reviewer's own findings, so it is left out.

[`handoff-facts.ts`](handoff-facts.ts) holds what the handoff commands read: the facts and the presumed snapshots, whether every finished attempt has its report recorded for this session with both files intact, and `takeSnapshot`, which turns a raw-check refusal into a snapshot that did not pass. When the snapshot passes, `takeSnapshot` also runs the attribute check on the candidate tree itself (batch review B07). Its root and nested `.gitattributes` blobs are read with `git cat-file` and judged from their contents by the same rule, so no candidate filter runs. A refusal stops `review`, `correct` and `close --finished` with `AttributeSourcesRefused`, and a read that failed with nothing read refused stops them with `AttributeSourcesUnread`, before any client gets the candidate. [`handoff-git.ts`](handoff-git.ts) builds the handoff's git work for a recorded worktree: the HEAD read, the attribute check, the snapshot and the changed paths, each pinned to the session's recorded identity. Its `headWith` is the one HEAD read, `git rev-parse HEAD` decoded as a revision, which the startup check uses too. [`recorded-files.ts`](recorded-files.ts) reads a file the log records and checks its hash first (`RecordedFileChanged`). [`brief-files.ts`](brief-files.ts) checks each attempt's recorded brief the same way: an attempt of the open session with no brief recorded, or with its brief file missing or changed, counts as a report that is not intact, so `review` and `correct` refuse with `ReportsNotIntact`.

[`handoff.ts`](handoff.ts) holds the handoff commands that launch nothing. `reject [--note]` appends `HandoffRejected` for a usable attempt awaiting its handoff, after which only `close --abandoned` remains. `closeFinished`, behind `session close --finished --attest`, runs the settle step and checks its rules with the snapshot presumed on the reviewed tree. Only then does it read the worktree's HEAD with `git rev-parse HEAD` through the runner pinned to the session's recorded identity, with no identity or attribute check, and check the rules again with that HEAD. A HEAD that is not the session's base refuses the close with `HeadMoved` before anything is staged; a read that fails keeps its own `GitCommandFailed` or `GitOutputUndecodable`. Then it runs the attribute check and takes the snapshot. When the tree is still the reviewed one, it appends `ReviewChecked`, `SessionClosed` with the attestation and a `WaiverExpired` for every armed waiver, in one batch.

[`session.ts`](session.ts) holds the other commands that launch nothing. `openSession` publishes a copy of the task file and appends `SessionOpened` and `Approved` for the tranche at the worktree's HEAD. `stepEnded` appends `StepEndedByOwner` at the wall clock's time. `closeSession` closes `--abandoned` or `--interrupted`: it runs the settle step, then appends `SessionClosed` and a `WaiverExpired` for every armed waiver. It releases no hold, deletes no file and changes grants only through settlement. Of these, only `session open` needs the worktree check, so `step-ended` and `close` stay available when the worktree or a client is broken. When the check could not run, `session open` stops with that failure, such as `GitCommandFailed`, rather than with a refusal.

[`status.ts`](status.ts) builds the status report over a `StatusContext` ([`status-context.ts`](status-context.ts)), which holds reads only: the log's read, the ledger's rows read without the write lock, the process listing, the version reads, the worktree check and the state files' read. It has no lock and nothing that appends or publishes. [`production-status.ts`](production-status.ts) builds that context in production without creating or writing anything. It opens the log and the ledger read-only, and only when their files exist (Runtime's `state-read.ts`), and reports `StateMissing` for a state directory with no log. A missing ledger reads as no rows, and the report's `ledgerFound` says so. It shows the session state, each incomplete attempt with its grant, the holds in place, the armed waivers, each client's pin check, the worktree check (a check that could not run shows as not passed, with the failure as its detail), the `headMoved` finding while a session is open and the checked HEAD is not its base, the integrity of each recorded report file and of each attempt's recorded brief, and the snapshot coverage statement, the same one each review brief states. It lists advisory process evidence for every attempt of the open session, finished ones included, because a leader's normal exit does not show that its descendants stopped. An attempt with `Intended` but no `Launched` is `LaunchUnknown`: the client is spawned before batch L, so it may have started and may still run. Every report states that the evidence is advisory: a group id may be reused, a descendant that left the group is not listed, and an unrecorded launch may have happened.

[`worktree-command.ts`](worktree-command.ts) holds `createRecordedWorktree`, behind `tarlatan worktree create`. Plan "Slice A1" does not name this command; it exists because a session needs a recorded worktree. Under the lock it refuses when the log already records a worktree (`WorktreeAlreadyRecorded`), so creation runs at most once. Otherwise it creates the worktree and appends `WorktreeCreated`. It does not write `WorktreeIntended` or recover anything. A crash between the add and the append leaves a worktree the log does not record; the next creation refuses its branch or path, and the owner resolves that.

[`session-context.ts`](session-context.ts) declares what a command runs over: the injected capabilities, such as the log, the ledger, the lock, `StartClient`, the profile publisher and the worktree check, and the settings from the configuration.

### A moved HEAD

While a session is open, the supervisor worktree's HEAD must stay at the session's base revision (owner ruling of 2026-11-23). Claude's profile denies `git commit`, and its sandbox denies writes to both git directories. A HEAD that moved anyway, from a commit made in the worktree or a command the agent ran, refuses `implement`, `review`, `correct` and `session close --finished` with `HeadMoved`. The refusal lists the base and the HEAD. The rule is in Features (`movedHead` in `command-refusals.ts`). The launches take the HEAD from the startup check's read, and `close --finished` from its own read. The startup check keeps that HEAD when it judges the worktree's attribute sources refused. A launch is then refused for both reasons, and `status` shows both (owner finding F2, dogfood-3a round 1). A HEAD read that fails is a failure, never this refusal, so it keeps every armed waiver. That holds beside refused attribute sources too (owner finding F2, round 2). When an attribute source could not be read after the HEAD was read, a launch stops with `AttributeSourcesUnread`. It keeps the waivers. `status` then shows the unread source beside the moved HEAD (owner finding F3). A launch refused for it expires them, as any launch refusal does. A refused `close --finished` leaves them armed (owner ruling, dogfood-3a round 1). `reject`, `step-ended`, `session close --abandoned` and `session close --interrupted` are never refused for it and still run no git command. `status` shows the moved HEAD as its `headMoved` finding and writes nothing.

The owner's recovery step: inspect `git log <base>..HEAD` in the supervisor worktree, reset the branch to the base if those commits are not wanted, and then close the session or continue it. Abandoning without that step leaves the next session based on the moved HEAD, so the agent's commit would never be reviewed.

## Production wiring

[`production.ts`](production.ts) builds the context in four steps. Nothing is opened or run before the first two finish, and nothing is made before them except a missing state or ledger directory, just before the binding is recorded.

First, [`production-target.ts`](production-target.ts) decodes the configuration and settles the ledger's directory. The file is read as strict UTF-8: bytes that are not UTF-8 fail with `FileNotUtf8` and never become U+FFFD (focused review finding 3). [`layout.ts`](layout.ts) then resolves the configured paths and checks the layout rules (batch review B05). The state directory and the supervisor worktree must lie outside the owner's checkout. The owner's checkout, the state directory and the ledger must lie outside the supervisor worktree. A broken rule fails with `LayoutRefused`.

Second, [`target-binding.ts`](target-binding.ts) binds the state directory to its target (batch review B04). The binding file, `<stateDir>/target-binding.json`, records the project id, the owner's checkout, the supervisor worktree's path and branch name, the ledger file and the attribute allowance, with every path canonical. It is read as strict UTF-8 too; a binding whose bytes are not UTF-8 is `TargetBindingUnreadable`, which `status` reports as a finding. A binding whose ledger path is not absolute is `TargetBindingUnreadable` too, with a reason that says so, since tarlatan only records absolute paths and a relative one would open the ledger relative to the working directory (owner finding F11). A command that acts on the target records the binding at first use, exclusively. When a binding is already recorded, the command first compares the configuration with it, so a configuration that names another target fails with `TargetMismatch` before any directory is read for creation or created (owner finding F10). That comparison comes before the layout rules, so a changed target that the layout check would refuse still fails with `TargetMismatch` (owner finding F10, dogfood-2b round 2). On first use the layout rules run before the binding is recorded. Then, before it records a first binding, [`store-directory.ts`](store-directory.ts) prepares the state directory and the ledger's directory, after the configured layout has passed. It judges both before it creates either, so a refused ledger directory leaves no state directory, binding or git `HOME` (owner finding F7, dogfood-2). The ledger's directory is the parent of the ledger file, the part of its path before the last `/` (owner finding F8). When nothing is at the path and its parent is a directory, Runtime creates that one directory with mode 0700 and sets the mode again, so the umask cannot change it. Features then judges what is there. An existing directory is used as it is, and its mode is not changed. A missing parent fails with `StoreDirectoryParentMissing`, which records the directory and its parent, and nothing is created. The path is resolved first, as the layout check resolves it, so a symbolic link to a directory is followed and that directory is used (owner ruling, dogfood-2). A dangling link cannot be resolved and fails with `LayoutRefused`, as before. A resolved path that is not a directory or cannot be read fails with `StoreDirectoryRefused`, which records the path (dogfood-1 finding). So does a directory whose mode `chmod` could not set to 0700 after `mkdir` made it. The binding is compared again when it is recorded, so a command that recorded another target first in a race is refused with `TargetMismatch` as well. That covers `worktree create`, `session open`, every launch, `reject` and `close --finished`. `status`, `step-ended` and `session close --abandoned | --interrupted` stay reachable. Those exits never fail with `TargetMismatch`: they run on the recorded target whatever the configured layout says, so a mismatched or broken configuration cannot block the way out of a session, and a changed `ledgerDir` is never created by them (assisted-cycle plan, focused review item 2; owner finding F10, dogfood-2). The facade builds `step-ended` and the two closes with their own constructions, described below, which run on the recorded target and record nothing; `status` has its own read-only construction, also described below. The layout of the target in force is checked again, since it may be the recorded one.

Third, [`git-home.ts`](git-home.ts) prepares git's `HOME`, `<stateDir>/git-home` (batch review B02). When nothing is at the path it creates a fresh directory with mode 0700, and Features then judges what is there. A home that holds anything, is a link, belongs to another user or has any mode but 0700 is refused with `GitHomeRefused`. Nothing at the path is cleared or changed, so a planted `HOME/.config/git/attributes` never reaches git.

Fourth, it opens the project's log and lock in the state directory and the ledger at `<ledgerDir>/ledger.sqlite`, and wires every capability from Runtime. The ledger is the owner's one ledger, shared by every project's state directory, with `~/.tarlatan` as the default directory (design "Where the ledger lives", batch review B09). Each project keeps its own log and lock. The state directory also holds the session's published files. Each handoff's git work runs through `handoffGitWith(startGit, target.attributeAllowance)`. Every role's grant estimate is the policy's `initialEstimate`, 15 points (decision P5); the configuration has no estimates. The monotonic clock is not wired yet (`nowMono` is none), so pacing answers Unknown and every launch needs `--waive`.

[`production-exits.ts`](production-exits.ts) builds the owner's exits (re-review R02): `step-ended` with `stepEndedProduction` and `session close --abandoned | --interrupted` with `exitProduction`. They run no git command. Their target comes from `exitTarget` in [`production-target.ts`](production-target.ts), which reads the binding before it looks at the configured layout, as `status` does (plan AC1, focused review finding 2). When a binding is recorded, the recorded target is in force, and a configured layout that breaks a rule blocks no exit. When none is recorded, the configured target is in force and its layout is checked. Before the binding is read, `exitTarget` refuses a state directory whose resolved path holds something that is not a directory. That refusal is `StoreDirectoryRefused`, with the path in it (owner finding F2, dogfood-2). Either way the layout of the target in force is checked with the state directory, and an unreadable binding refuses the exit with `TargetBindingUnreadable`. `stepEndedProduction` then prepares the state directory and opens only the log and the lock; `step-ended` never reads the ledger, so it never opens it. `exitProduction` judges the state directory and the ledger's directory before it creates either, then opens the log, the lock and the ledger, which the close's settle step writes. Both prepare a directory as `production` does (`store-directory.ts`). It never prepares or judges git's `HOME`, so a contaminated `<stateDir>/git-home` blocks no exit; the commands still refuse whatever their own rules refuse. Every command that runs git is built by `production` and still refuses that home. `stepEnded` takes a `StepEndedContext`, the log and the lock, and `closeSession` an `ExitContext`, which adds the ledger and the project; each is the part of a `SessionContext` the command uses.

`exitTarget` reads the binding before it settles the ledger's directory (focused re-review finding 3). With a binding recorded, the exits use the recorded ledger, so a configuration without `ledgerDir` works when `HOME` is unset. The default `<HOME>/.tarlatan` is resolved only when no binding is recorded. An unset `HOME` then fails with `ConfigUndecodable`, as it does for every command that settles the configured target.

SQLite's `-shm` coordination file is the one file that may change (owner ruling on B11, 2026-11-20). It holds neither the lock nor a write transaction. It stays reachable under a configuration that names another target. It decodes the configuration, then [`status-target.ts`](status-target.ts) settles the target it runs on without failing. Three problems become findings in the output: a configured layout that breaks a rule or cannot be resolved (`ConfiguredLayoutRefused`, which also covers a default ledger directory that cannot be settled because `HOME` is unset; follow-up review at 3b72efc, finding 4), a binding that cannot be read or decoded (`TargetBindingUnreadable`) and a recorded target whose layout breaks a rule (`RecordedLayoutRefused`).
