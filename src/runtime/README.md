# Runtime

See [how it works](../../docs/how-it-works.md).

May import: `domain`.

Per the [design](../../docs/plans/2026-11-14-agent-supervisor-design.md) ("Architecture"), this layer is the Effect shell: launching agent processes in a new process group, the SQLite event store with its conditional append, the instance lock, the clock, the walk and digest of protected paths, git reads and the commit and reset procedures, and a notifier (a log notifier in the first version). Persistent state lives here and passes through the pure Features functions. The sections below describe the parts built so far. The layer table lets Runtime import only Domain, so decisions stay out of it. The owner approved the design and Part B's first milestone (Tasks B1 to B10).

## Ledger store

[`ledger-sqlite.ts`](ledger-sqlite.ts) implements Domain's `LedgerStore` on a SQLite file through Bun's built-in `bun:sqlite` ([intake record](../../docs/dependency-intake.md)). Each record kind has its own table, and a one-row `ledgerSeq` table numbers every row across all tables. Each write is one `BEGIN IMMEDIATE` transaction, so seq order is commit order. A transaction that fails rolls back with no row written and no seq used. A second charge or cancel of a grant is skipped, and a charge of a canceled grant (or the reverse) fails with `GrantSettled`. A write that waits longer than `busy_timeout` for another connection's lock fails with `LedgerBusy` and writes nothing. The file records its format version in SQLite's `user_version` header field (dogfood-5). Opening the ledger reads that field on a read-only connection first, so a ledger stamped by a newer release fails with `StoreVersionNewer`, and one stamped below 0 with `LedgerError`, before any read-write connection exists; such a ledger is left byte for byte as it was. Otherwise the open takes WAL mode, then reads the version again inside one `BEGIN IMMEDIATE` transaction, refuses on that read, creates any missing table and stamps a ledger at 0 (written by v0.1.0) with 1. Its version is decided against `knownLedgerVersion`, 1, and the ledger is never raised. A current ledger is not written, and no version is ever lowered. A lock held past `busy_timeout` at that transaction fails the open with `LedgerBusy`. [`bun-sqlite.d.ts`](bun-sqlite.d.ts) declares the parts of `bun:sqlite` the store uses, since the project installs no Bun type package.

Tests run on the Bun runtime (`bun --bun vitest run`), so they reach `bun:sqlite` against temporary database files.

## Project log and lock

[`project-log.ts`](project-log.ts) implements Domain's `ProjectLog`: one SQLite table of events numbered from 1. Each append includes the position its writer last read and runs in one `BEGIN IMMEDIATE` transaction. If another writer appended first, the append fails with `PositionMoved` and writes nothing. The writer then re-reads the log and decides again. The log's format version is checked and stamped as the ledger's is. It is decided against the log's own known version, `knownLogVersion` (2), and refused with the log's own errors: a log above 2 fails with `StoreVersionNewer`, a negative one with `ProjectLogError`, and a lock held past `busy_timeout` at the open with `ProjectLogError` ("project log busy"). A log at 0 is stamped 1 and a new log is created at 1, as before; a log at 1 is read and appended to as it is. Every open now takes the write lock briefly, so it can wait up to `busy_timeout`. The one raise (v0.2.0): inside an append's `BEGIN IMMEDIATE` transaction, after the position check passes and before the inserts, the version is read again. When the append holds an event Domain's `raisesLogFormat` names (today `FindingsRecorded`) and the log reads 1, or 0 after a raw reset, the append sets `user_version` to 2; the raise commits and rolls back with the inserts, since the field is on page 1. A version read there that is above 2 or below 0, which only another connection could have stamped since the open, fails the append with `ProjectLogError` naming that version and the known one, and nothing is written.

[`state-read.ts`](state-read.ts) opens the log and the ledger for `status` only to read. A store whose file is missing gives none, and nothing is created: each file is opened read-only, and only when it is there. The open reads the store's format version and stamps nothing; each reader exposes it as `version`, so 0 means a store v0.1.0 wrote that no writer has opened since. Each store is decided against its own known version (the log 2, the ledger 1). A store stamped newer than that, or below 0, fails the open with `StoreVersionNewer` or the store's own error before any row is read. Each read of rows runs in one deferred transaction, which never takes the write lock, so the read is a consistent snapshot while another connection writes. Its first statement reads the version again, and Domain's decision on that read governs the read. At any version this release reads (0, the known version, or for the log also 1), the rows are read, so a store stamped from 0 to 1, or a log raised from 1 to 2, since the open reads normally. A store stamped newer or below 0 since the open is refused as at the open, and no row is read. A reader's one connection holds one transaction at a time, so each reader's reads, `openLedgerReading`'s included, queue on a one-permit semaphore made when the reader is opened, as the writers' transactions do. `openLedgerReading` opens the ledger and reads it once for status, and gives the version that read found with either the rows or the refusal as a value. Like every reader of a WAL database, it records its read mark in SQLite's shared-memory index (`-shm`); the database file and its WAL file are not written. This holds because every writer asks SQLite, through `keepWalFiles` in [`sqlite.ts`](sqlite.ts), to keep the WAL and `-shm` files when it closes. Bun's bundled SQLite on Linux deletes them otherwise, and a read-only connection would then create both and could not remove them. Apple's SQLite, which Bun uses on macOS, keeps them already.

[`project-lock.ts`](project-lock.ts) gives one holder at a time and refuses a second at once with `LockHeld`. Bun has no `flock`, so the lock is SQLite's exclusive lock on a dedicated lock file, held with `busy_timeout` 0. SQLite's unix locks are POSIX advisory locks, which the operating system drops when the holder's process dies. [`sqlite.ts`](sqlite.ts) holds what the stores share. It recognizes `SQLITE_BUSY` and reads an error's message. Its `readStoreVersion` decodes `PRAGMA user_version` with a Schema and passes the number to Domain's `decideStoreVersion`. Its `openWriter` is the writers' open in the order above; each store passes in its own error mapping.

## Supervisor worktree

[`worktree.ts`](worktree.ts) adds the supervisor worktree from the owner's checkout (plan B11a). It runs commands and reports raw results; Program decides. `readOwnerHeadWith` returns the owner's `rev-parse HEAD` output. `probeBranchWith` returns the branch probe's exit code and output. `addWorktreeWith` runs `git worktree add --lock --reason tarlatan -b <branch> -- <path> <base>` and cleans nothing up. `readAddedWith` then takes the raw reads: the requested path's `realpath` and four single-value `rev-parse` outputs (top level, HEAD's full ref, git directory, common directory), each from its own command. A failed command keeps its args, exit code and stderr. `listWorktreesWith` returns the text of `git worktree list --porcelain -z`. [`worktree-directory.ts`](worktree-directory.ts) holds `readDirectoryWith`, which reports what `stat` found at the recorded path (nothing, a file or a directory) and, inside a directory, the full results of the two identity `rev-parse` commands, whatever they exit with, and [`file-paths.ts`](file-paths.ts) holds the `stat` and `realpath` reads. `statOf` reports nothing there only for ENOENT or ENOTDIR; any other error, such as an unsearchable parent, fails with `PathUnreadable`. Git runs through an injected `RunGit`. In production that is the clean runner, except that the session commands read the supervisor worktree's HEAD with `readOwnerHeadWith` over the pinned runner. [`node-child-process.d.ts`](node-child-process.d.ts) declares the Node calls Runtime uses, since the project installs no Node type package.

[`attribute-sources.ts`](attribute-sources.ts) holds the attribute check's reads (plan B11c). `listTreeWith` runs `git ls-tree --full-tree -r -t -z <revision>`, `readBlobWith` runs `git cat-file blob <object>`, `readAttributesFileSettingWith` runs `git config --get core.attributesFile` and `readConditionalIncludesWith` runs `git config --get-regexp '^includeif\.'`; each returns the run whatever it exited with, and none applies attributes. `readFileAt` reports what `lstat` found at `<commonDir>/info/attributes` without following a symlink: nothing, the kind with a regular file's text, or the failure's message.

## Git environment

[`git.ts`](git.ts) holds the clean runner (plan B11b, design "Git environment"). `cleanGit(home)` runs every command with exactly five environment variables: `PATH=/usr/bin:/bin`, `HOME` set to the empty directory the caller passes, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_ATTR_SOURCE` set to git's empty tree. Nothing comes from the parent. Each command starts with `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c commit.gpgsign=false`. So no hook, fsmonitor program, `gpg.program` or filter declared in `.gitattributes` runs, no global or system config is read, and a `GIT_DIR` in the parent cannot pick the repository. `startGit` is the process call beneath it: `execFile` with an explicit environment, on whose PATH Bun resolves `git`. It reads stdout and stderr as raw bytes and decodes each as strict UTF-8 through [`strict-utf8.ts`](strict-utf8.ts), keeping a leading byte order mark (review finding B17). Bytes that are not UTF-8 fail the run with `GitCommandFailed`, git's exit code and `undecodableOutput` as its `stderr`, before any caller checks a path or content. A lossy decoder would turn them into U+FFFD, and a path with such bytes could then collide with a genuine U+FFFD path. This is the only module that runs git. The process gate, `test/runtime/git-process-gate.test.ts`, checks on the syntax tree that only four modules may start a process, named by path: this one, [`spawn.ts`](spawn.ts), [`processes.ts`](processes.ts) and [`client-version.ts`](client-version.ts). It also requires an explicit `env` on every `execFile` and `spawn` call, and lets only this module pass `git` as the program. The repository's own `.git/config` still applies; `--no-verify` comes with a later slice.

`pinnedGitWith(start)(home)(identity)` is the pinned runner (plan B11d, design "Supervisor worktree"). It takes a worktree's recorded identity as typed input: `path`, `gitDir` and `commonDir`, the fields of `WorktreeCreated`. Each command runs with the clean runner's five variables plus exactly three: `GIT_DIR=<gitDir>`, `GIT_WORK_TREE=<path>`, `GIT_COMMON_DIR=<commonDir>`. The three overrides and the output and failure rules are the clean runner's. It reads nothing to find these values, so a `.git` file that names another repository, a `commondir` file that names another common directory, a `core.worktree` setting and a parent `GIT_DIR`, `GIT_WORK_TREE` or `GIT_COMMON_DIR` do not move its reads (`test/runtime/git-pinned.test.ts`). Under git 2.50.1 refs are still found through the worktree's `commondir` file, so it does not guard ref reads against that file. A `rev-parse` run through it prints the values it was given, so it cannot verify an identity. The startup attribute check runs through it, and so does the session commands' read of the supervisor worktree's HEAD once that check passes; see the [Program README](../program/README.md).

`snapshotGitWith(start)(home)(identity)(indexFile)` is the snapshot runner (plan A2): the pinned runner plus `GIT_INDEX_FILE`, exactly nine variables, with the same three overrides. `read-tree`, `add` and `write-tree` then use `indexFile`, and the worktree's own index is never read or written. The caller supplies a fresh path; the runner neither makes nor checks it.

## Snapshot

[`snapshot.ts`](snapshot.ts) holds the snapshot's commands (`snapshotArgs`): the object-format check; the preflight's `ls-tree --full-tree -r -z <base>`, `ls-files -z --others --ignored --exclude-standard --directory` and `check-ignore -q -- ./<path>` (review finding B08); then `read-tree <base>`, `add -A`, `write-tree` and `ls-tree --full-tree -r -z <tree>`. `withTemporaryIndex` makes a new directory in the state directory, passes the path of an index file inside it that does not exist yet, and removes the directory however the use ends; it fails with `SnapshotIndexFailed` when the directory cannot be made. `sha1` is the platform's SHA-1 through `node:crypto`, which Format's `blobId` takes as its digest.

[`worktree-entries.ts`](worktree-entries.ts) holds `readWorktreeEntry`, which reports what is on disk at one tree entry's path without following a link at the path itself. `lstat` decides the kind. A symbolic link gives its link text through `readlink`, and its target is never opened. A regular file is opened with `O_NOFOLLOW`, so a link swapped in at the final component after the `lstat` fails instead of being followed, and its bytes and executable bit come from that open descriptor. Any other kind is reported and not read. It never fails: an error becomes `EntryUnreadable` with its message.

[`worktree-walk.ts`](worktree-walk.ts) holds `listDirectory`, the preflight's listing of one directory (review finding B08). `readdir` gives each name as raw bytes, decoded as strict UTF-8, and `lstat` gives each entry's kind without following a link at that entry. Entries come sorted by name, and none is opened. It never fails: a directory it cannot list, an entry it cannot inspect, or a name that is not UTF-8 becomes `DirectoryUnlisted` with the reason.

These reads have a limit (review L02). `lstat`, `readlink` and `O_NOFOLLOW` guard only the final component of a path. The directories above it are resolved as they stand, so a directory swapped for a link to somewhere outside the worktree between staging and the reads would redirect them. The snapshot's observations assume the assisted rung's quiescence: no concurrent writer changes the worktree while a snapshot runs. Nothing here defends against one.

## Client processes

[`spawn.ts`](spawn.ts) starts a client (`StartClient`) with exactly the `ClientLaunch` it is given. The client inherits nothing and runs as the leader of a new session and process group, so its group id is its pid. Stdin reads from `/dev/null`. Every byte of stdout and stderr is appended to the raw file as it arrives, and stdout is also streamed as lines. [`stdout-lines.ts`](stdout-lines.ts) puts each line together from its bytes across chunk boundaries and only then decodes it as strict UTF-8 (review finding R04). A line whose bytes are not UTF-8 arrives as an `UndecodableLine`, never as text with U+FFFD in it, and a character split across two chunks decodes whole. The split is Effect's `Stream.splitLines` over byte text, one character per byte, which finds the same line ends because `\n` and `\r` never occur inside a multi-byte UTF-8 sequence. Right after spawn it reads the leader's start time once through the injected process listing; that time is none when the read failed. `exit` completes once the leader has exited and its output has closed, and fails with `RawOutputFailed` when the raw file could not be fully written. Nothing here sends a signal: the declared child type has no `kill`, and interrupting a consumer leaves the client running.

[`processes.ts`](processes.ts) reads the process listing, `ps -A -o pid,pgid,lstart,command`, as raw text. It runs `/bin/ps` by absolute path with `LC_ALL=C` as its whole environment, so the layout is the C locale's and nothing from tarlatan's environment reaches it. A failed start, a non-zero exit or a signal fails with `ProcessReadFailed`.

[`client-version.ts`](client-version.ts) runs `<client> --version` with an explicit environment and directory. The client's name is resolved on that environment's PATH. It returns the output and exit code whatever the exit. It fails with `ClientStartFailed` only when the client could not start or a signal ended it. Features compares the output with the pin.

## State files

[`state-files.ts`](state-files.ts) reads and publishes the files that events name by path and SHA-256, such as an attempt's handoff. `publish` writes `<path>.tmp`, flushes it, renames it over `path` and flushes the directory, so the final name holds either the earlier file or the complete new one. It returns the SHA-256 of the bytes it was given. A stale `<path>.tmp` from an interrupted publish is overwritten, and any failure is `StateFileFailed`. The directory's descriptor is closed even when its flush fails, and the flush failure is the one reported. `readIfPresent` gives none only when no file is at the path; a file it cannot read fails.

## Git's private HOME

[`git-home.ts`](git-home.ts) reads what is at git's `HOME` path without following a link (`readHome`) and creates the directory (`createHome`, batch review B02). Creation makes one directory with mode 0700 and sets that mode again, so the umask cannot change it. Nothing here removes, empties or changes an existing entry.

## State and ledger directories

[`store-directory.ts`](store-directory.ts) reads what is at the state directory's or the ledger directory's path without following a link (`readStoreDirectory`) and creates the directory (`createStoreDirectory`, dogfood-1 finding). When nothing is at the path, the reading also says whether the parent is a directory. Program passes the resolved path, so a link is seen here only when one appeared after the path was resolved. Creation makes only the last component, with mode 0700, and sets that mode again, so the umask cannot change it; a missing parent makes creation fail. A failed `mkdir` is `StoreDirectoryUnreadable`, and a failed `chmod` after it is `StoreDirectoryModeUnset`, which Program never discards. Nothing here removes or changes an existing entry.

## Canonical paths

[`canonical-path.ts`](canonical-path.ts) holds `canonicalPathOf` (batch review B05). It resolves a path's nearest existing ancestor with `realpath` and appends the components below it as given, so a path not made yet still resolves through any link above it. An entry that exists but cannot be resolved, such as a dangling link, fails with `PathUnreadable` and is never read as absent.

## Target binding file

[`binding-file.ts`](binding-file.ts) reads the target binding when it is present and creates it at most once (batch review B04). Creation writes the bytes to a temporary file of its own, flushes them and links that file to the final name with link(2), which fails when the name exists. The final name therefore holds a complete file or nothing, two first uses cannot both win, and an existing binding is never replaced.
